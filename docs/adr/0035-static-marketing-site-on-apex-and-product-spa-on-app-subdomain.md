# Static marketing site on the apex and the product SPA on an app subdomain

PocketCircle serves two origins from one zone. `https://pocketcircle.app` is a marketing **Site** — a new `apps/site` package that builds to static HTML and is served by its own Cloudflare Worker with static assets and no `main`, so asset requests are free and unlimited and never consume the Workers Free plan's daily Worker-invocation budget. `https://app.pocketcircle.app` is the authenticated product app, unchanged in every other respect: the same React Router SPA-mode build (ADR 0017), the same assets-only Worker and SPA fallback (ADR 0007), now claimed under the app subdomain. This delivers the intent ADR 0004 already recorded — marketing kept separate so it can use static generation for SEO without forcing the authenticated app into a server runtime — and it resolves the interim state where the marketing page was baked into the SPA shell as `HydrateFallback` purely to satisfy crawlers.

The homepage is statically generated, not server-rendered, because per-request rendering of `/` is both unnecessary and impossible to make session-aware. Google OAuth branding needs real first-byte HTML describing the product with a Privacy link on the verified domain, and static generation delivers exactly that with less machinery. Session awareness is unavailable to any apex runtime by construction: the cross-domain auth client stores the session in origin-scoped `localStorage` and replays it to the Convex-hosted auth routes as a request header with `credentials: "omit"`, so no server on a different origin can read it. Making `/` a real server render would additionally require a Worker runtime for the product document, spend billable invocations on every app request, contradict the no-server-runtime decision in ADR 0017 and the assets-only decision in ADR 0007, and still leave the flash it was meant to fix — a static marketing origin removes the flash at the root, because the marketing document and the app document are never the same document, so there is no post-hydrate swap to be jarring.

A subdomain is used instead of a path carve-out such as `pocketcircle.app/app`, because a path prefix rewrites every deep link, poisons the PWA `start_url` and `scope`, forces a base path through the whole app, and permanently muddies which origin owns which surface. A subdomain keeps product URLs clean, keeps the marketing origin free of any auth trust, and leaves room for a future marketing Worker to grow edge behavior without touching the app.

Apex keeps canonical ownership of the marketing surfaces `/`, `/privacy`, `/terms`, `/support`, and `/whats-new`. These are the URLs already published in external submission material, and Privacy and Terms must sit on the same domain as the homepage for Google branding, so holding them on apex preserves every existing inbound citation. Every other apex path is not lost: the marketing Worker answers it with a `302` to the identical path on the app subdomain, declared in a static `_redirects` file, which Workers static assets serve without a Worker script and therefore without invocations. Bookmarks, shared Circle links, and already-delivered Invitation and Account Deletion emails keep resolving, so the move is not a URL break. One redirect family needs verification rather than assumption: the Account Deletion verification link carries its token in the query string, and the `_redirects` documentation lists query-parameter *matching* as unsupported, so passthrough of an untouched query on a plain redirect is confirmed against a preview deployment during the cutover, with a minimal Worker on the marketing origin restricted to those paths as the fallback if it does not hold.

The accepted cost is a single forced sign-out. Because the session lives in origin-scoped `localStorage` on the app origin, changing that origin signs every User out exactly once, and no cookie-domain mechanism can prevent it — `localStorage` has no domain attribute. Nothing is invalidated server-side: better-auth session rows stay valid, the auth secret is unchanged, and all Convex data, Circle history, and MCP grants are untouched, so returning is one tap of Continue with Google. Installed progressive-web-app launches follow the new `start_url` on the app subdomain, and a small number of cosmetic device-local keys (last-used Google email, dismissed prompts) reset. A one-time client-side resume shim that hands the stored session token to the new origin in a URL fragment remains possible, because a fragment is never sent to a server or a `Referer`, but it is deliberately deferred: it is permanent surface area to carry and delete on a schedule, and it should be built only if Users actually report the re-auth as a problem.

The Site is deployed by the existing tag-driven GitHub Actions pipeline as a third Wrangler deploy alongside the app and MCP Workers, and both marketing and product Workers expose `workers.dev` URLs so every artifact is verifiable before the cutover. Because two Workers cannot both claim one hostname, the apex handover is sequenced back-to-back in a single run and carries a sub-minute gap on the marketing homepage only; the app subdomain is deployed and verified first, while apex is still the app, so the cutover is a formality rather than a discovery.

Cloudflare Pages was rejected because it has been feature-frozen since April 2025, Cloudflare steers new projects toward Workers static assets, and Workers keeps assets, `_headers`, and `_redirects` in the same version-controlled config with the option to add a `main` later without changing hosting products. Rendering the product app server-side on Workers was rejected for the reasons above. A single-origin split with the app under a path was rejected because it still requires a routing Worker and still rewrites every product URL. Branding-only workarounds inside the SPA shell — the interim `HydrateFallback` arrangement and its build assertion — are removed by this decision rather than kept as a permanent contract, because the marketing origin now serves that HTML honestly.
