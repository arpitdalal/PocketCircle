# TanStack Form for shared web and native form state

PocketCircle standardizes on [TanStack Form](https://tanstack.com/form) (`@tanstack/react-form`) as the single form-state convention across the codebase, replacing the per-field `useState` boilerplate currently hand-rolled in each form (Transactions, Categories, and every form to come). The driver is not just removing boilerplate but establishing one form mental model — field state, dirty tracking, blur/submit validation timing, error reveal — that holds for `apps/web-app` today and the planned React Native app later. TanStack Form is headless, controlled-by-default, and renderer-agnostic, so the same `useForm` shape, the same validators, and the same domain schemas drive both platforms; only the leaf field components differ (DOM inputs on web, `TextInput` on native).

Validation reuses the existing Zod schemas (ADR 0010) directly via Standard Schema — no resolver adapter — and the server remains the authority (ADR 0015); the form is a courtesy mirror. To keep the form library fed with a shape it can actually validate per-field, the domain layer splits the transforming `transactionInputSchema` into a pure-input `transactionFormSchema` (no transform, what the form binds to and validates) plus an explicit `toMutationArgs` transform (form values → Convex mutation args, e.g. major-unit amount string → integer minor units per ADR 0009, and `paidBy` self-collapse). Both halves are framework-agnostic and live in `packages/domain`, so the future native form imports them unchanged; the web-only shadcn `Field` components stay in `apps/web-app`. The split also lets the seam be typed end-to-end, removing the lone `as` cast the single-schema approach forced.

The house validation-timing convention is on-blur-then-live: field-level `onBlur` validators give early feedback, errors are revealed only when `(isBlurred && isDirty) || submissionAttempts > 0` — so tabbing through an untouched field stays silent and "required" surfaces at submit, while an edited-but-invalid field flags on blur — and a form-level `onSubmit` validator against the full `transactionFormSchema` is the authoritative gate. Non-text fields (Category chips, Paid By select) bind through `field.handleChange` and validate on change/submit rather than blur.

Web implements the shared field kit with TanStack Form’s `createFormHookContexts` + `createFormHook` (`apps/web-app/app/lib/form.tsx`): pre-bound leaf components share one `useFieldReveal()` helper implementing `(isBlurred && isDirty) || submissionAttempts > 0`; `AmountField` only calls `handleChange` after blur when `onBlurNormalize` returns non-null so an empty untouched amount does not flip dirty on tab-through. `SelectField` keeps Paid-by-specific props optional. `formComponents` includes the transaction submit row. Exports: `useAppForm`, `useTypedAppFormContext` (TanStack’s supported pattern for typed subtrees under `AppForm`). `withForm` is not re-exported: the Transaction form’s Type (edit) + Category blocks live in dedicated modules instead; Category uses `useTypedAppFormContext` with the module-scope `transactionFormContextOptions` from `transactionFormOptions()` so `form.Subscribe` / `form.Field` stay typed to `TransactionFormValues` without prop-drilling the form handle. One `transactionFormOptions()` declaration feeds both `useAppForm` and `useTypedAppFormContext`, so the typed subtree cannot drift from the form it reads.

The Transaction form itself is composed as one shared controller plus one shared field body rather than a self-contained form component (issue #297). `useTransactionForm` (`apps/web-app/app/components/transaction-form/use-transaction-form.ts`) is a headless hook that owns everything stateful about the form: the TanStack form instance, the Category and Member reads, inline Category creation bookkeeping, domain validation and the create/update mutations, submission errors, product analytics, and the completion result — a successful submission resolves through an `onComplete` callback carrying the created Transaction’s id and the exact submitted values (or the updated id), so the hosting route can build its own canonical destination; the controller never navigates. `TransactionFormBody` renders every field — Title, Amount, Date, Categories with inline creation, Paid By, Note — plus validation messages, submit state, and the accessible edit Type-Change confirmation; it holds no reads or mutations of its own, and no route defines a second Transaction field tree. Route adapters sit above both: each route supplies the current Circle, the intent (a create Type + date-default month, or an edit target), analytics context, and callbacks, and keeps for itself what only a URL owner can decide — URL state, initialization timing, confirmation decisions (an approved Type Change routes back into the controller via `applyTypeChange`), and navigation. Because hooks cannot be conditionally mounted, adapters render the controller+body pair in a child component gated behind their guards, and remount-by-key remains the re-initialization mechanism: a changed input (a different create Type or edit target) produces a fresh form with fresh defaults instead of any in-place reset or route-owned duplication.

Standalone Category creation (issue #305) stays a single-route form — no controller/body split — but uses the same foundation. `categoryFormOptions()` (`apps/web-app/app/components/category-form-options.ts`) is the reusable values + validators contract: mount-time defaults (URL-seeded Type, empty Name, one-shot random Color) plus `categoryInputSchema` as the form-level `onSubmit` Standard Schema gate. Form values are typed as `CategoryFormValues` (`z.input` of that schema) so Color stays a string on the form side while parse output narrows to a palette id. `NewCategoryForm` binds Name through shared `TextField` (with optional `onUserChange` to clear a stale mutation error, and `describedBy` / `externallyInvalid` so a form-level mutation rejection stays associated with Name without becoming a field-schema error), and binds the existing `Segmented` Type control and `ColorPicker` through `field.handleChange` without duplicating their UI. Name uses the on-blur-then-live reveal rule via `categoryInputSchema.shape.name`; Type and Color are constrained widgets whose validity is gated at submit by the form-level schema (same change/submit convention ADR 0020 uses for non-text Transaction fields). Submit stays attemptable when Name is blank so an invalid attempt reveals “Name is required”; only a pending mutation disables actions. `onSubmit` re-parses with `categoryInputSchema` and sends that parsed output (trimmed Name included) to `createCategory`. Server/mutation failures stay distinct from field validation — mapped through `mutationErrorMessageForUser`, rendered inline with a stable id, draft preserved, form unlocked for retry — and a stale mutation error clears when Name or Type changes. The route alone owns navigation: success and Cancel invoke `onClose`, which returns to the validated `returnTo` or the safe Categories fallback.

## Considered alternatives

- **React Hook Form** — the more mature, more popular default, and shadcn's original `Form` integration. Rejected primarily on the native goal: RHF's core advantage is *uncontrolled* DOM inputs via `register()`, which React Native cannot use, forcing a `<Controller>` around every field and diverging the web and native binding styles. This app's forms are custom-controlled-widget-heavy anyway, so RHF would pay the controlled-path cost on web while never cashing its uncontrolled edge. shadcn now ships a TanStack Form integration as well, neutralizing the remaining web-DX argument.
- **Conform** — server-action and progressive-enhancement first. Eliminated by the SPA mode of ADR 0017 (no server `action`) and irrelevant to a native client.
- **Formik / Final Form** — stagnant maintenance and no first-class Zod/Standard-Schema path.
