# Web Push notification constraints

Research date: 2026-08-27. Scope: [issue #309](https://github.com/arpitdalal/PocketCircle/issues/309), after product chose true Web Push while PocketCircle is closed and one push for every Notification Center event. Sources are browser-vendor documentation, web standards, MDN, and repository source.

## Verdict

Do not request notification permission on app load. PocketCircle needs an explicit, contextual **Enable notifications** control. The native request must run directly from that user action. Firefox suppresses prompts without prior interaction, Safari requires direct interaction for iPhone/iPad Home Screen web apps, and Chrome may put low-acceptance origins or users who frequently deny prompts into quiet UI. Chrome and Mozilla both recommend contextual prompting rather than first-visit prompting. [Mozilla: Firefox permission prompt restrictions](https://blog.mozilla.org/futurereleases/2019/11/04/restricting-notification-permission-prompts-in-firefox/) · [WebKit: Web Push on iOS/iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) · [Chromium: quieter notification permission UI](https://blog.chromium.org/2020/01/introducing-quieter-permission-ui-for.html) · [Chrome: notification permission data and recommended patterns](https://developer.chrome.com/blog/notification-permission-data-in-crux)

True closed-app delivery requires a service worker, Push API subscription, application server sender, and persistent notification created with `ServiceWorkerRegistration.showNotification()`. Push messages are delivered to a service worker even when the web page is inactive; MDN explicitly describes notifications when the page is out of focus or closed. [W3C Push API](https://www.w3.org/TR/push-api/) · [MDN: re-engageable notifications](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Tutorials/js13kGames/Re-engageable_Notifications_Push)

## Hard platform constraints

- Notification permission and Push API access require a secure context. `Notification.requestPermission()` resolves to `granted`, `denied`, or `default`; `default` means no known decision and must be treated like denial. Chrome and Firefox do not permit notification requests from cross-origin iframes. [MDN: `Notification.requestPermission()`](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static) · [MDN: using Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)
- Permission requests and `PushManager.subscribe()` should occur from a user gesture. Firefox has required interaction since version 72; Safari's iOS/iPadOS flow requires the subscription call immediately from the gesture handler. [Mozilla](https://blog.mozilla.org/futurereleases/2019/11/04/restricting-notification-permission-prompts-in-firefox/) · [Apple Developer: Sending web push notifications](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) · [MDN: `PushManager.subscribe()`](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)
- The web app cannot revoke or reset a browser permission. The Permissions API exposes status but no supported `revoke()` operation; users change a denial in browser or OS settings. [MDN: Permissions API](https://developer.mozilla.org/en-US/docs/Web/API/Permissions_API)
- `Notification.permission === "default"` does not distinguish never asked from dismissed or otherwise undecided. PocketCircle therefore needs its own non-authoritative prompt-history state if it wants to suppress or defer its explanatory UI; that state cannot replace the browser's actual permission status. This is an inference from the API's three states and `default` definition. [MDN: `Notification.requestPermission()`](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static)
- On iPhone and iPad, Web Push is supported for web apps added to the Home Screen from iOS/iPadOS 16.4 onward, and permission must be requested from direct interaction inside that installed web app. Web notifications then integrate with Lock Screen, Notification Center, Focus, and paired Apple Watch. A normal browser tab is not the supported iOS Web Push surface. [WebKit: Web Push on iOS/iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- Safari supports standards-based Web Push for webpages on macOS and Home Screen web apps on iOS/iPadOS. It requires every received push to produce a visible notification immediately; Safari can revoke permission when a site receives pushes without doing so. [Apple Developer: Sending web push notifications](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)
- On most mobile browsers, `new Notification()` throws. Persistent cross-platform notifications must use a service worker's `showNotification()`. [MDN: using Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API) · [MDN: `showNotification()`](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)
- Chrome and Edge require `userVisibleOnly: true` for push subscription. Safari also requires user-visible pushes. Silent/background-only push is not a portable product capability. [MDN: `PushManager.subscribe()`](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe) · [WebKit: Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)
- Push is queued delivery, not an exact-time guarantee. The sender supplies a TTL; an undelivered message is removed when it expires, and a push service may reduce the TTL. [Chrome/web.dev: Web Push protocol](https://web.dev/articles/push-notifications-web-push-protocol)

## Browser intervention and prompting

Chrome's quiet notification UI can be enabled for users who repeatedly deny prompts and automatically for origins with very low acceptance rates. Chrome also applies stronger treatment to abusive permission requests and notification content. [Chromium: quieter UI](https://blog.chromium.org/2020/01/introducing-quieter-permission-ui-for.html) · [Chromium: abusive notification content](https://blog.chromium.org/2020/10/reducing-abusive-notification-content.html)

Firefox requires a tap, click, or key press before showing a prompt; without interaction it shows only an address-bar icon. Mozilla explicitly endorses informative in-content controls that match the page instead of imitating browser UI. [Mozilla: Firefox permission prompt restrictions](https://blog.mozilla.org/futurereleases/2019/11/04/restricting-notification-permission-prompts-in-firefox/)

Chrome's current guidance is to let users opt in through existing UI at a relevant workflow moment and avoid prompts or overlays immediately on arrival. Chrome 155 plans an even lighter Android prompt whose request may time out to `default`, with later grants possible through Site Controls; PocketCircle should observe permission changes rather than assuming the request Promise is the only transition. Chrome 152 is the stable release as of this research date, so the Chrome 155 behavior is forward compatibility, not a current baseline. [Chrome: recommended notification patterns](https://developer.chrome.com/blog/notification-permission-data-in-crux) · [Chrome: lighter Android notification prompts](https://developer.chrome.com/blog/notification-prompts-android) · [Chrome 152 release notes](https://developer.chrome.com/release-notes/152)

## Installation requirements by platform

| Platform | Normal secure browser site | Installed web app |
| --- | --- | --- |
| iPhone and iPad | Web Push unavailable | Required: add to Home Screen and open as a web app |
| Android Chrome, Firefox, and Edge | Web Push available | Optional |
| Desktop Chrome, Edge, Firefox, and Safari | Web Push available | Optional |

On iOS and iPadOS 16.4 or later, only a Home Screen web app can request Web Push permission. On iOS and iPadOS 26, **Add to Home Screen** must retain **Open as Web App**; a browser bookmark is not enough. Installation can start from any browser that exposes Add to Home Screen, not only Safari. [WebKit: iOS/iPadOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) · [WebKit: iOS/iPadOS 26 web apps](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) · [Apple: use web apps on iPhone](https://support.apple.com/en-ie/guide/iphone/iphea86e5236/ios)

Android and desktop browsers expose standards-based Push to normal secure websites; installation changes launch and presentation, not Push eligibility. The Push API can receive while the site is not loaded, subject to the browser process and push service. Firefox for Android receives website Push through Mozilla's service plus Google Cloud Messaging without requiring installation. [MDN: Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API) · [Mozilla: Web Push in Firefox](https://support.mozilla.org/en-US/kb/push-notifications-firefox)

Closed-page behavior varies. Safari on macOS Ventura or later can deliver while Safari is not running, and Microsoft Edge on supported Windows versions can deliver while Edge is closed. Desktop Chrome delivers with no site windows open while its background process remains running, but not after the browser fully quits; desktop Firefox requires Firefox to be open and otherwise queues subject to expiry. These differences do not depend on PWA installation. [WebKit: Web Push on macOS](https://webkit.org/blog/12945/meet-web-push/) · [Microsoft: Edge Web Push while closed](https://blogs.windows.com/msedgedev/2020/11/16/improving-notifications-badging-microsoft-edge/) · [Google: Push notifications FAQ](https://web.dev/articles/push-notifications-faq) · [Mozilla: Web Push in Firefox](https://support.mozilla.org/en-US/kb/push-notifications-firefox)

## Subscription and delivery model

A push subscription belongs to a service-worker registration and has a unique endpoint plus encryption material. The browser or push service may refresh or deactivate it at any time. Unregistering the service worker deactivates its associated subscription. [W3C Push API, subscriptions](https://www.w3.org/TR/push-api/#push-subscription)

The endpoint can address that particular subscription and should be kept secret. Invalid or expired endpoints return `404` or `410` and must be removed server-side. [MDN: `PushSubscription.endpoint`](https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/endpoint) · [Chrome/web.dev: Web Push protocol responses](https://web.dev/articles/push-notifications-web-push-protocol#response_from_push_service)

Consequent product model:

- Store zero-to-many **device/browser subscriptions per User**, not a single `notificationsEnabled` boolean. Browser permission, PocketCircle preference, and usable subscription are separate states. This follows from subscriptions being unique delivery contexts that can refresh or expire. [W3C Push API](https://www.w3.org/TR/push-api/#push-subscription)
- Reconcile `pushManager.getSubscription()` on authenticated app startup/focus and process subscription refresh/change where supported; also prune `404`/`410` responses. Do not send pushes merely to keep a subscription alive. [W3C Push API, subscription refreshes](https://www.w3.org/TR/push-api/#subscription-refreshes) · [Chrome/web.dev: expired subscriptions](https://web.dev/articles/push-notifications-web-push-protocol#response_from_push_service)
- Bind each endpoint to the currently authenticated PocketCircle User. On logout or account switch, remove that server association before another account can inherit the same origin/browser subscription. This is a security recommendation inferred from an endpoint targeting a browser/service-worker subscription rather than an application account. [MDN: `PushSubscription.endpoint`](https://developer.mozilla.org/en-US/docs/Web/API/PushSubscription/endpoint)
- Treat the Notification Center row as source of truth and Web Push as best-effort delivery. Issue #309's “mirror every event” means enqueue push from the same created notification identity, not recreate event rules in a second writer. The existing event set and actor-skip policy already live in [NTF-2](../issues/NTF-2-notification-events.md); current notification creation is explicitly best-effort in [ADR 0027](../adr/0027-best-effort-notification-fan-out-via-scheduler.md).

## Notification content and interaction

PocketCircle notifications can appear on an iPhone/iPad Lock Screen and other OS surfaces. Because this is financial software, default push copy should avoid amounts and other sensitive details; use the existing ID-free title/body or more generic copy, and let the authenticated destination reveal detail. The platform-display fact is from WebKit; minimizing sensitive lock-screen content is a product recommendation. [WebKit: Web Push on iOS/iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

The service worker can handle `notificationclick`, focus an existing same-origin client, or open a same-origin URL. Exact URL matching is unreliable for an SPA that changes routes client-side, so the robust flow is to focus an existing PocketCircle client and message it to navigate, or open the canonical URL when no client exists. [MDN: `Clients.openWindow()`](https://developer.mozilla.org/en-US/docs/Web/API/Clients/openWindow) · [MDN: `notificationclick`](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event)

If every Notification Center event must remain individually represented, omit `tag` or use the notification row ID as a unique tag. Reusing a tag replaces the prior pending/displayed notification. [MDN: replacing existing notifications](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API#replacing_existing_notifications)

Keep actions optional. `notificationclick` itself is not MDN Baseline across all widely used browsers, and action-button presentation varies by platform. A body click to the canonical authenticated destination is the portable core. [MDN: `notificationclick`](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event) · [MDN: `showNotification()` options](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)

## PocketCircle readiness

PocketCircle already publishes a manifest with `display: "standalone"`, `/` scope/start URL, and 192/512 icons, so it meets the older iOS manifest display requirement for opening as a Home Screen web app. It lacks a stable manifest `id`, which WebKit uses as an installed-web-app identity input for cross-device Focus settings. [site.webmanifest](../../apps/web-app/public/site.webmanifest) · [WebKit: manifest ID](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/#manifest-id)

No service-worker or Push/Notifications API implementation exists in the current web app. Therefore #309 is not a permission-dialog-only feature: it adds service-worker lifecycle, subscription persistence, VAPID/Web Push sending, endpoint cleanup, click routing, authenticated account rebinding, and platform-specific onboarding.

## Settled product flow

1. Expose **Enable notifications on this device** in Settings. Also show one dismissible announcement strip in normal document flow above the sticky app header on the first eligible authenticated app visit after a new User finishes required profile confirmation, or on an existing User's first visit on that device after the feature ships. The strip may wrap on mobile but must scroll away with the page rather than remain fixed or sticky. Never invoke the native permission request automatically; only its **Enable notifications** action may invoke it.
   The strip may coexist with the separate Feature Announcement card. The existing full-screen PWA install dialog takes visual precedence while open and naturally covers both; neither underlying element needs to be hidden merely because it is mounted.
   On an uninstalled iPhone or iPad, dismissing that one-time install dialog also suppresses the notification strip because the browser tab cannot enable Push. Settings remains available and explains that installation is required before notifications can be enabled.
2. Feature-detect service workers, Push API, and Notifications API. On iOS/iPadOS where PocketCircle is not running as a Home Screen web app, explain **Add to Home Screen** before offering notification permission.
   In Settings on an uninstalled iPhone or iPad, show an **Install PocketCircle** button with “Install PocketCircle to enable notifications on this iPhone.” Do not show a switch that cannot change state. Inside the installed app, replace that prerequisite action with the notification switch.
   On the first launch inside the newly installed iPhone or iPad app, show the notification announcement strip unless notifications are already enabled or blocked there. Its action can now request notification permission; dismissing the install prerequisite in a browser tab does not suppress this installed-app prompt.
3. On the explicit enable action, request permission and subscribe. Dismissing either the PocketCircle strip or a native prompt permanently suppresses the strip on that device; Settings remains available. If permission is denied, replace the switch with **Blocked in browser settings** plus recovery instructions because PocketCircle cannot request again. If permission remains `default`, Settings allows another explicit attempt.
4. Mirror each newly created Notification Center row to every active subscription for its recipient. Preserve the settled event title, but replace the body with generic copy that contains no Member, Circle, Transaction, or Category names. Use the row ID as delivery identity/idempotency key and unique OS tag. The whole notification is one tap target; v1 has no event-specific action buttons.
5. Treat Push Notification delivery as best-effort. Retry transient sends, remove expired endpoints, expose no delivery status, and keep the Notification Center as the source of truth. Normal activity Pushes expire from the push service after 24 hours; Invitation Pushes expire no later than their Invitation deadline.
6. On click, close the OS notification, authenticate, resolve the current access-checked canonical destination, and open or focus PocketCircle there. If the destination no longer exists or the User lacks access, open the Notification Center with the matching row instead. Mark the row read only after this resolution succeeds; failures leave it unread.
7. Provide **Disable notifications on this device** by unsubscribing and removing that endpoint while leaving the browser's granted permission intact. Re-enabling explicitly creates a fresh subscription without another native prompt. A User may enable each browser or installed app independently; there is no account-wide switch or other-device list. Every subscribed device receives each Push Notification. Sign-out first unsubscribes locally and removes the server binding; signing in again requires explicit re-enablement.
8. Support every capable standards-based desktop and Android browser. Support iOS/iPadOS 16.4 or later through installed Home Screen web apps.
9. Register a production service worker only for Push receipt, notification clicks, and subscription lifecycle. It has no `fetch` handler, cache, offline shell, or offline-write behavior.
10. Record only coarse product events: announcement impression and dismissal, permission result, enabled, disabled, and notification opened. Apply the existing analytics opt-out. Never include names, notification titles, endpoint material, object IDs, or notification IDs in analytics.
11. Do not add PocketCircle quiet hours. Users control suppression through operating-system Focus, Do Not Disturb, and notification settings.
12. Limit each User to ten active subscriptions. On enable, prune invalid subscriptions first; if ten remain, replace the least recently seen one. Reconciliation on authenticated startup and focus refreshes `lastSeenAt`. Settings manages only the current device.

## Sender architecture options

PocketCircle currently has no Web Push, Firebase, or OneSignal dependency. Its Convex package already depends on `@convex-dev/workpool`; external email delivery already uses internal actions and deployment-scoped environment variables. [Convex package](../../packages/convex/package.json) · [email action](../../packages/convex/convex/email.ts)

### Direct standards-based VAPID

The application stores each browser's standard `PushSubscription` and POSTs an encrypted, VAPID-authenticated payload directly to the endpoint selected by that browser. This remains cross-vendor: Chrome, Firefox, and Safari select their own push services. Apple says an existing standards-based Web Push implementation works on iPhone/iPad and requires neither an Apple Developer Program membership nor a proprietary Safari protocol. [Apple Developer: Web Push](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) · [WebKit: iOS/iPadOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

[`web-push`](https://github.com/web-push-libs/web-push) is the established Node package for this path. It implements payload encryption and VAPID, generates the key pair, supports Safari 16+, exposes TTL/urgency/topic, and returns the push service's status, headers, and body. Its repository remains active, but its latest tagged release is `v3.6.5` from 2023; pin and audit it rather than treating release cadence as a maintenance guarantee. [web-push README](https://github.com/web-push-libs/web-push#readme) · [web-push releases](https://github.com/web-push-libs/web-push/releases)

The package uses Node APIs, so it belongs in a dedicated Convex `"use node"` internal-action module. Convex supports Node 20/22/24 actions; only actions may use the Node runtime or make external requests. PocketCircle's mutations must enqueue the sender after notification creation rather than call the network inline. [Convex runtimes](https://docs.convex.dev/functions/runtimes) · [Convex actions](https://docs.convex.dev/functions/actions)

A Web-Crypto/fetch-only package could run in Convex's faster default runtime, but visible candidates are much less established. `@block65/webcrypto-web-push` documents Node/Worker/Deno support but has a small user base; `negrel/webpush` explicitly says it has not been reviewed by crypto experts. Saving a Node cold start is not worth choosing a lightly proven cryptographic implementation. [block65/webcrypto-web-push](https://github.com/block65/webcrypto-web-push) · [negrel/webpush security warning](https://github.com/negrel/webpush)

Direct Web Push has no messaging-vendor subscription fee. PocketCircle still pays its existing Convex action/function and network usage. A successful Web Push POST means the push service accepted the message, not that the device displayed or the User saw it; the response does provide actionable `404`/`410` invalid-endpoint cleanup. [Web Push protocol responses](https://web.dev/articles/push-notifications-web-push-protocol#response_from_push_service)

### Firebase Cloud Messaging for Web

FCM's Web SDK uses service workers and VAPID but gives the application Firebase Installation/registration tokens. Sending targets the FCM HTTP v1 API using a Firebase project and a short-lived OAuth 2.0 access token derived from a service account. The current Firebase support matrix lists Cloud Messaging for Chrome, Firefox, Safari, and iOS Safari, so Apple compatibility is not a reason to prefer direct sending over FCM. [FCM Web setup](https://firebase.google.com/docs/cloud-messaging/web/get-started) · [Firebase JS supported environments](https://firebase.google.com/docs/web/environments-js-sdk) · [FCM server environment](https://firebase.google.com/docs/cloud-messaging/server-environment)

FCM is no-cost and can import an existing VAPID pair. It returns a message ID on accepted sends and identifies invalid/expired registrations with `UNREGISTERED`/HTTP 404, or `INVALID_ARGUMENT` only after ruling out payload errors. Firebase's documented delivery-data export is for native Android/Apple SDKs, not Web Push, so FCM does not provide a portable browser display receipt advantage for PocketCircle. [Firebase pricing](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans) · [FCM Web VAPID import](https://firebase.google.com/docs/cloud-messaging/web/get-started#configure_web_credentials_with_fcm) · [FCM send response](https://firebase.google.com/docs/cloud-messaging/send/v1-api#send_messages_to_specific_devices) · [FCM token cleanup](https://firebase.google.com/docs/cloud-messaging/manage-tokens) · [FCM delivery reporting](https://firebase.google.com/docs/cloud-messaging/understand-delivery)

For this web-only transactional use case, FCM adds a Firebase client SDK, Firebase Installation identity, project/service-account credential, OAuth token generation, and provider-specific send API while PocketCircle must still build permission UX, a service worker, User mapping, cleanup, and click routing. Its benefit is Google-operated infrastructure and a future common API for native apps; neither is required by #309 today.

### OneSignal

OneSignal manages browser/device subscription records, invalid-token transitions, API sending, dashboard reports, and optional display/click/dismiss webhooks. It supports iOS/iPadOS 16.4+ Home Screen web apps but still requires OneSignal's client SDK and service worker on PocketCircle's origin. Safari provides none of OneSignal's display/click/dismiss webhooks; Firefox lacks dismiss, so even this hosted option cannot prove cross-browser delivery or viewing. [OneSignal Web Push setup](https://documentation.onesignal.com/docs/en/web-push-setup) · [OneSignal subscriptions](https://documentation.onesignal.com/docs/en/subscriptions) · [OneSignal webhooks](https://documentation.onesignal.com/docs/en/webhooks)

Current pricing allows Web Push on the free plan with at most 10,000 subscribers per send. Growth starts at $19/month plus $0.004 per Web Push subscriber; each subscribed browser counts separately. PocketCircle's one-recipient transactional sends fit the free per-send limit, but subscriber-priced cost and plan terms become an ongoing dependency. [OneSignal pricing](https://onesignal.com/pricing) · [OneSignal billing definitions](https://documentation.onesignal.com/docs/en/billing-faq)

OneSignal can export subscription data, including Web Push token fields, but its migration guide says Web Push subscriptions cannot be imported or transferred directly between provider/app identities. Users must revisit the same origin for silent re-registration, and service-worker URL migrations can require keeping the old worker available for at least a year. This is recoverable lock-in, not a clean server-side switch. [OneSignal export](https://documentation.onesignal.com/docs/en/exporting-data) · [OneSignal migration](https://documentation.onesignal.com/docs/en/migrating-to-onesignal) · [OneSignal service-worker migration](https://documentation.onesignal.com/docs/en/onesignal-service-worker)

### Secrets, rotation, and failure handling

For direct VAPID, generate one production key pair once. Publish the public key to the client and store the private key plus VAPID contact subject in deployment-scoped Convex environment variables; Convex explicitly supports environment variables for API keys and other secrets. Keep separate development/production pairs. [web-push key guidance](https://github.com/web-push-libs/web-push#generatevapidkeys) · [Convex environment variables](https://docs.convex.dev/production/environment-variables)

VAPID key rotation is a subscription migration, not a transparent secret swap. The public key restricts the subscription to the matching private key; Push API subscription options cannot change. To rotate, retain the old private key, issue the new public key, have returning clients unsubscribe/resubscribe, record which VAPID key each subscription uses, and keep sending old subscriptions with the old key during a bounded transition. A compromised old key requires invalidating its subscriptions rather than silently replacing it. [RFC 8292 subscription restriction](https://www.rfc-editor.org/rfc/rfc8292.html#section-4) · [W3C Push API subscription options](https://www.w3.org/TR/push-api/#pushsubscriptionoptions-interface)

Convex scheduled actions execute at most once and are not automatically retried on transient failures. Web Push POSTs are external; repeated sends can be made user-visible-idempotent by reusing the Notification Center row ID as the OS `tag`. Use a dedicated Push Workpool with bounded concurrency and limited exponential-backoff retries, isolated from the email Workpool so a slow push provider cannot starve Invitation email. Keep their combined configured concurrency below Convex's action limit. Workpool requires retryable actions to be idempotent and provides configurable retries plus `onComplete`; permanent `404`/`410` responses should bypass retry and delete the subscription. [Convex scheduled-function guarantees](https://docs.convex.dev/scheduling/scheduled-functions#error-handling) · [Convex Workpool](https://github.com/get-convex/workpool#durable-reliable-workflows) · [Web Push invalid endpoint responses](https://web.dev/articles/push-notifications-web-push-protocol#response_from_push_service)

### Recommendation

Use direct standards-based VAPID with pinned `web-push` in a Convex Node internal action, queued per subscription through a dedicated Push Workpool with low parallelism and bounded retry. Keep subscription ownership, notification identity, endpoint cleanup, and delivery outcome in PocketCircle. This is the smallest architecture that fully supports Chrome, Firefox, Safari/macOS, and iOS/iPadOS Home Screen apps without adding a second user/device system.

Do not choose FCM for v1: it adds Firebase identity and OAuth machinery but no required browser coverage or delivery receipt that direct Web Push lacks. Do not choose OneSignal for v1: its dashboard analytics and managed lifecycle are real benefits, but PocketCircle's events, recipients, copy, and source-of-truth rows already exist in Convex, while OneSignal adds client/service-worker control, third-party User mapping, subscriber pricing, and a revisit-dependent exit path. Reconsider a hosted vendor only if marketing segmentation, campaign authoring, cross-channel messaging, or vendor-operated analytics becomes an explicit product requirement.
